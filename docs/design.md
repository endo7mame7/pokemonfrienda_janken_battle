# ピックじゃんけんバトル 設計ドキュメント

ポケモンフレンダのピックを使った、じゃんけん型対戦ゲームの設計書です。
実装は `index.html` の単一ファイルに閉じており、本書はその内部構造・仕様・設計判断をまとめたものです。

- 対象読者: このプロトタイプを改修・拡張する開発者
- 対応する実装: `index.html`（約1450行）
- 本書中の `index.html:442` のような表記は、該当コードの行番号を指します

---

## 1. コンセプトと設計方針

### 1.1 想定する遊び方

**幼稚園児2人が、1台のiPhoneを間に置いて向かい合って遊ぶ。**

この1文がほぼ全ての設計判断の根拠になっています。

| 前提 | 設計上の帰結 |
| --- | --- |
| 対面で1台を共有する | 画面を上下2分割し、プレイヤー2側のUIを180°回転（`index.html:134`） |
| 相手に手の内が見える | 「じゃん・けん・ぽん」の合図まで選んだ手を伏せる（`index.html:1082`） |
| 文字が読めない／読み始め | 全文ひらがな、絵文字と色でも判別可能に |
| 指が小さく誤タップしやすい | 手の選択は**500msの長押し**で確定（`index.html:1096`） |
| 集中が続かない | 1バトル = ハート3つ。1対1なら数十秒で決着 |
| じゃんけんは運だけ | 負けているほうに きずなが多く貯まり、メガシンカで逆転できる |
| 手持ちが増えると飽きる | 1対1／2対2／3対3 の勝ち抜き戦を選べる |
| 写真に公式イラストが写る | 登録データを端末外に出さない（送信処理を一切持たない） |

### 1.2 技術方針

- **単一HTMLファイル**。ビルド工程・パッケージマネージャ・サーバ不要
- **外部依存は Google Fonts のみ**（Dela Gothic One / M PLUS Rounded 1c）。JSライブラリはゼロ
- **画像・音声アセットを持たない**。ピック外形も、サンプルピックも、集中線も、効果音もすべて実行時生成
- iOS Safari で「ホーム画面に追加」すると全画面起動する（`apple-mobile-web-app-capable`）

この方針により、配布は「HTMLを1つ開くだけ」で完結し、リポジトリに著作物を一切含めずに済んでいます。

## 5. データモデル

### 5.0 チーム編成（`index.html:544`–`566`）

勝ち抜き戦のため、選択状態は「1体」ではなく「出場順の配列」で持ちます。

```js
let teamSize = 1;              // 1 | 2 | 3
const team = {1:[], 2:[]};     // team[p][i] = i番目に出るピックのid
```

**ルール**

| 項目 | 仕様 |
| --- | --- |
| 人数 | 1対1／2対2／3対3。登録枚数を超える人数は選べない（`maxN = min(3, picks.length)`） |
| チーム内の重複 | 不可。同じピックを1チームに2枠置けない |
| 相手チームとの重複 | 可。登録が2枚でも 2対2 が成立するようにするため |
| ハート | 人数にかかわらず常に3つ（`MAXHP`） |

`fitTeams()`（`index.html:553`）が編成を常に正規化します。

```
team[p] を teamSize 個に切り詰める／伸ばす
  ↓
消されたピックのidを null にする
  ↓
チーム内で重複しているものを null にする
  ↓
空き枠を「まだ使っていないピック」で自動的に埋める
   （相手チームとも重複しないものを優先し、足りなければ重複を許す）
```

`renderHome()` の冒頭で必ず呼ばれるため、**ずかんでピックを消してもホームに戻れば編成が破綻しない**という性質が成り立ちます。空き枠を自動で埋めるので、人数を切り替えた直後からそのままバトルを始められます。

**設計判断: 重複を弾かずに「入れ替え」にした理由**
えらぶ画面で、同じチームの別の枠が使っているピックを選んだときは、拒否するのではなく
**2つの枠を入れ替えます**（`index.html:649`）。
拒否だと「なぜ選べないのか」を読めない子に説明する手段がなく、
かといって重複を許すとルールが壊れます。入れ替えなら空き枠が生まれず、
出場順の並べ替えという本来やりたい操作もそのまま実現できます。

### 5.0.1 メガシンカ（`index.html:453`）

**メガシンカ技を設定したピックだけがメガシンカできます。** ずかん登録時に4つの技から選び、
「メガシンカ しない」を選べば ふつうのピックになります。これが「特定のポケモンだけ」の実装です。

```js
const MEGA = [
  ['crit',  'かいしんの いちげき', 'かつと ハートを 2つ けずる',           '#ff5d52'],
  ['guard', 'まもりの かべ',       'まけても ハートが へらない',           '#3ddc97'],
  ['drain', 'いのちを すいとる',   'かつと けずって じぶんも 1つ かいふく', '#c56bff'],
  ['storm', 'あらしの ちから',     'あいこでも あいてを 1つ けずる',       '#23b8e8'],
];
```

**技の名前は ずかん登録で自由に決められます**（`pick.megaMove`）。
通常わざと同じように入力欄があり、メガシンカ技を選んだときだけ現れます。
未入力なら `MEGA` の既定名（上の表の2列目）がそのまま使われるので、
名前を決めなくても遊べますし、**旧データもそのまま既定名で動きます**。

```js
const megaMoveOf = pk => pk?.megaMove || megaInfo(pk?.mega)?.[1] || '';
```

`MEGA` の2列目は「効果の名前」と「既定の技名」を兼ねています。
ずかんのカードには**技名（虹バッジ）と効果の説明を並べて**出すので、
名前を変えても どの効果なのか分からなくなりません。

`pick.mega` にキーを持ち、未設定（`null` / 旧データの `undefined`）ならメガシンカ不可です。
**保存済みのピックは `mega` を持たないため自動的にメガシンカ不可**になり、データ移行は要りません。

**設計判断: 4つの技が どれも「相打ち」を生まないこと**
ダメージを与えるのは常に *その回に勝ったほう* だけ、という不変条件を保っています。
`counter`（負けても相手に返す）のような技を入れると両者同時KOが起こり、
引き分け画面という子どもに説明しづらい状態を作る必要が出ます。
唯一あいこでダメージが出る `storm` も、**両方が `storm` なら ぶつかり合って相殺**させることで、
同時KOの経路をふさいでいます（`index.html:1134`）。

### 5.1 ピック（Pick）

アプリが扱う唯一の永続エンティティです。

```js
{
  id:      'p-1737000000000',  // 'p-' + Date.now()。サンプルは 's-' + name
  name:    'ケケンカニ',        // 表示名（必須・最大14文字）
  type:    'みず',              // TYPES の表示名のいずれか
  move:    'ばくれつパンチ',     // 技名（最大14文字・未入力なら「たいあたり」）
  orient:  'h',                 // 'h' = よこむき / 'v' = たてむき
  img:     'data:image/png;base64,...', // 切り抜き済みPNG（長辺720px）
  created: 1737000000000,       // 並び順に使用
  sample:  true                 // サンプルピックのみ付与（任意）
}
```

**設計判断: 画像を dataURL で持つ理由**
Blob ではなく dataURL を採用したのは、`<img src>` への即時代入、Canvas への再描画、
IndexedDB への構造化クローン保存がすべて追加処理なしで通るためです。
オブジェクトURLのライフサイクル管理が不要になり、コード量を大きく削減しています。
代償としてサイズが約33%増えますが、長辺720pxのPNG（数百KB）であり、
端末ローカル保存のみなので許容しています。

### 5.2 タイプ（`TYPES` / `index.html:442`）

18タイプを `[表示名, カラー, エフェクト種別]` の3要素配列で定義します。

```js
['ほのお', '#f0582a', 'fire']
```

- **カラー**: ずかんのチップ、カットインの背景、サンプル生成のグラデーションに使用
- **エフェクト種別**: パーティクル定義 `FX` のキー。**18タイプ → 10種**に集約されます

| エフェクト | 割り当てられるタイプ |
| --- | --- |
| `normal` | ノーマル |
| `fire` | ほのお |
| `water` | みず |
| `elec` | でんき |
| `grass` | くさ、むし |
| `ice` | こおり |
| `fight` | かくとう、じめん、いわ、はがね |
| `ghost` | どく、ゴースト、あく |
| `wind` | ひこう、ドラゴン |
| `psy` | エスパー、フェアリー |

18種すべてに固有エフェクトを作らず「見た目の印象が近いもの」でまとめる判断です。
タイプの識別はチップの色が担うため、演出の作り分けは10種で十分としています。
`typeInfo()`（`index.html:449`）は未知のタイプに対して `TYPES[0]`（ノーマル）を返すため、
データが壊れていても描画は落ちません。

### 5.3 永続化（`index.html:486`–`511`）

IndexedDB `pick-janken` / objectStore `picks`（keyPath: `id`）。

```
store.all()  → created 昇順の配列を返す
store.put(p) → メモリMapとIndexedDBの両方へ書き込む
store.del(id)→ 両方から削除
```

**フォールバック設計**: `db()`（`index.html:488`）は失敗時に `null` で解決する Promise を返し（reject しない）、
`tx()` は `null` を受けると `Map` を使ったメモリ処理へ切り替えます。
プライベートブラウズや IndexedDB が無効な環境でも、その場では遊べる状態を保ちます。
`put` が Map にも常に書くのは、この切り替えを呼び出し側から見えなくするためです。

### 5.4 サンプルピック（`samplePick()` / `index.html:519`）

登録が0件のとき、Canvas で図形生成した2枚を自動投入します（`loadPicks()` / `index.html:534`）。

- 「サンプル ほのお」（よこむき・🔥）と「サンプル でんき」（たてむき・⚡）
- タイプ色のグラデーション矩形に絵文字を重ね、`SAMPLE` の文字を焼き込む
- `pickPath()` でクリップするため、実物と同じ外形になる

**公式画像を一切含めずに、起動直後から遊べる状態を作る**ための仕組みです。
横向き・縦向きを1枚ずつにしてあるので、両方のレイアウトが初回から確認できます。

## 6. ピックの外形仕様

実物のフレンダピックを模した角丸長方形を、`pickPath()`（`index.html:474`）が定義します。

```
RATIO = 1.62（長辺 / 短辺）

通常の角     : 半径 = 短辺 × 0.09
ボールマーク側: 半径 = 短辺 × 0.21  ← 1角だけ大きい
  よこむき(h) → 左下
  たてむき(v) → 右下
```

```
   よこむき (h)                たてむき (v)
   ╭──────────────╮            ╭────────╮
   │              │            │        │
   │              │            │        │
   ╰───────────────╯           │        │
   ╰╯ ← 大きい丸み              ╰────────╯
                                      ╰╯ ← 大きい丸み
```

この1つの関数を、以下**4箇所すべて**で共用しているのが要点です。

1. エディタの切り抜き枠の描画（`draw()` / `index.html:761`）
2. エディタの枠外マスク（同上、`evenodd` で枠の外側だけを暗くする）
3. 保存時のクリップ（`index.html:861`）
4. サンプルピックの生成（`index.html:523`）

枠として見えている形と、保存される形が定義上ズレません。
表示側は CSS の `.ori-h` / `.ori-v`（`index.html:193`）が同じ 1.62 を使い、
`--L` に応じて縦横どちらかを基準にサイズを決めます。

## 7. 登録エディタ

### 7.1 画像の取り込み（`loadFile()` / `index.html:780`）

```
File → ObjectURL → Image → 長辺2200pxへ縮小して Canvas に確保 → ObjectURL を解放
```

- カメラ入力は `capture="environment"` 付きの `<input type="file">`（`index.html:389`）
- アルバム入力は `capture` なしの別 input
- 取り込み後は枠を埋める倍率の **1.6倍**を初期ズームにする。少し大きめに置くことで、
  「縮めて合わせる」という子どもにも分かりやすい操作から始められる
- `<input>` の `value` は毎回クリアし、同じ写真を続けて選び直せるようにしている

長辺2200pxの上限は、拡大操作に耐える解像度を保ちつつ、
端末のメモリを圧迫しないための妥協点です。

### 7.2 操作（`index.html:817`–`844`）

Pointer Events で統一的に処理します（タッチ／マウス／ペンを分岐しない）。

| 操作 | 効果 |
| --- | --- |
| 1本指ドラッグ | 移動（`ed.tx` / `ed.ty`） |
| 2本指ピンチ | 拡大・縮小（`ed.s`） |
| 2本指ひねり | 回転（`ed.rot`） |
| かたむきスライダー | 微調整 ±20°、0.5°刻み（`ed.fine`） |
| ↺ / ↻ 90° | 90°単位の回転 |
| ＋ / − ズーム | ボタンによる段階ズーム（×1.1） |
| はじめから | 取り込み直後の状態へ戻す |
| ホイール | 拡大・縮小（PC確認用） |

**ピンチの座標変換**（`index.html:831`）が本エディタで最も込み入った部分です。
2本指の中点を固定点として、そこからの相対ベクトルを回転・スケールしてから
中点の移動量を足し戻すことで、「つまんだ点が指の下に留まる」挙動を実現しています。
素直に中心基準で拡大すると画像が指から逃げ、幼児には操作不能になります。

回転を `ed.rot`（ジェスチャ・90°ボタン）と `ed.fine`（スライダー）に**分けて保持**しているのは、
スライダーが常に絶対値 0 を中心とした微調整として振る舞うようにするためです。
描画時に `ed.rot + ed.fine` として合成します（`index.html:756`）。

### 7.3 枠の計算（`frame()` / `index.html:745`）

Canvas の短辺の 86% を基準に、`RATIO` を保った最大の枠を中央へ配置します。
向き（`ed.orient`）の切り替えで枠の縦横が入れ替わります。
Canvas は `devicePixelRatio` を掛けたバッキングストアを持ち、`setTransform` で
CSSピクセル座標系に揃えてあるため、以降の描画コードは倍率を意識しません（`index.html:739`）。

### 7.3.1 既存ピックの修正（`openEditor(pk)` / `index.html:713`）

ずかんのカードをタップすると、そのピックを**なおす**モードでエディタが開きます。
`editingId` に対象のidが入り、見出し・ボタン・ヒントの文言が切り替わります。

**設計判断: 切り抜き済みの画像を そのまま `ed.img` に戻す**
元の写真は保存していないので、位置の取り直しはできません。
そこで**切り抜き済みの画像を枠にぴったり収まる倍率で読み込み直します**（`fitExisting()` / `index.html:688`）。
画像と枠は同じ比なので `ed.s = fw / img.width` で一致し、
写真を選び直さなければ 720px を等倍で描き直すだけなので 実質劣化しません。

この作りにより、**新規と修正で保存処理を分ける必要がありません**。
どちらも同じ切り抜きパイプラインを通り、`id` と `created` を引き継ぐかどうかだけが違います。

`ed.fromExisting` は「はじめから」の戻し先を決めるために持ちます。
既存画像なら枠ぴったりへ、撮り直した写真なら従来どおり 1.6倍のズームへ戻します。

**この機能がないと困ること**: メガシンカ技はあとから追加した項目なので、
**それ以前に登録したピックは `mega` を持たず、永久にメガシンカできません**。
修正できて初めて、手持ちのピックにメガシンカ技を設定できます。

### 8.2 状態（`B` / `index.html:972`）

```js
const B = {
  size:   1,                 // 1対1 / 2対2 / 3対3
  team:   {1:[], 2:[]},      // 出場順のピック実体（配列）
  hp:     {1:[], 2:[]},      // 各ピックの残りハート（team と同じ並び）
  idx:    {1:0, 2:0},        // いま出ているピックの位置
  choice: {1:null, 2:null},  // 確定した手（'gu'|'choki'|'pa'）
  busy:   false,             // 演出中の入力ロック
  over:   false              // 決着済み
};
const cur   = p => B.team[p][B.idx[p]];   // 出場中のピック
const curHp = p => B.hp[p][B.idx[p]] ?? 0;
```

ホーム側の `team`（idの配列）と、バトル側の `B.team`（ピック実体の配列）は別物です。
`startBattle()` で一度だけ実体へ解決するため、バトル中にずかんを触られても進行中の対戦は影響を受けません。

`B.idx[p]` が `B.size` に達した時点で、そのチームは全滅＝敗北です。

`busy` は、じゃんけんの判定演出が走っている間に手が押されるのを防ぐ唯一のガードです。
`lock()`（`index.html:1104`）と、手ボタンの長押し開始（`index.html:1095`）の両方で確認します。

### 8.2.1 きずなゲージとメガシンカ（`index.html:972`–`978`）

```js
B.bond     = {1:0, 2:0};          // 0〜100
B.megaUsed = {1:false, 2:false};  // バトル中 1回だけ
B.mega     = {1:0, 2:0};          // 発動中の のこりラウンド数
```

| 項目 | 仕様 |
| --- | --- |
| 貯まり方 | 負け +50 / 勝ち +25 / あいこ +15、それぞれ **0.8〜1.2倍のランダム係数** |
| 連敗ボーナス | 連敗が続くほど 1回あたり **+25 ずつ上乗せ**（2連敗目は +75、3連敗目は +100） |
| 発動条件 | 満タン、未使用、出ているピックがメガシンカ可、まだ手を決めていない |
| 継続 | **こうげきが1回起きるまで**（あいこでは消費しない） |
| 回数 | 制限なし。ゲージを溜め直せば 何度でも |
| 副作用 | なし |

**設計判断: 負けたほうに多く貯める**
じゃんけんは完全な運なので、勝っているほうがさらに強くなると一方的になります。
削られた側に多く貯めることで、ハートが残り1つでも「まだ何かできる」状態を作り、
最後まで泣かずに遊べるようにしています。

**設計判断: ランダム係数**
固定値だと「何回負けたら使える」が毎回同じになり、展開が読めてしまいます。
係数を掛けることで発動タイミングが毎回ずれ、同じ相手と続けて遊んでも飽きにくくなります。

**設計判断: 連敗ボーナス（`BOND_STREAK` / `index.html:466`）**
`B.streak[p]` が連敗数を持ち、負けるたびに `BOND_STREAK × (連敗数 - 1)` が上乗せされます。
勝つと 0 に戻り、あいこでは途切れません。

これにより **2連敗すれば係数が最小でも必ず満タン**になります（40 + 60 = 100）。
ハートは3つしかないので、2連敗は「あと1回で負ける」状況です。
そこで確実にメガシンカできることが保証されるため、
一方的に負けている子にも必ず一度は見せ場が回ってきます。

上乗せがかかったラウンドは、ゲージを一瞬光らせて音を鳴らします
（`boostBond()` / `index.html:1062`）。数字が読めない子にも「なにか良いことが起きた」と伝わります。

**なぜ1対1でも間に合うのか**: 1対1は決着まで3〜5ラウンドしかありません。
連敗ボーナスなしでも **2敗1勝すれば 40+40+20 = 100** で満タンになる重みにしてあり、
連敗した場合は2ラウンドで届きます。ここを軽くすると、1対1では一度も使えないまま試合が終わります。

**設計判断: あいこでは消費しない**
`MEGA_ROUNDS` は1で、`endRound(noAttack)` はこうげきが起きたラウンドだけ消費します。
あいこで何も起きなかった回に解けてしまうと、せっかく溜めたゲージが無駄になり、
「なんで消えたの」と言われてしまうためです。
「メガシンカは つぎの こうげき 1かいだけ」という約束にしてあります。

**設計判断: 回数を制限しない**
1ターンで解けるかわりに、ゲージを溜め直せば何度でも使えます。
1回きりだと「いつ使うか」を考える必要があり、幼児には重い判断になります。
溜まったら使う、を繰り返せるほうが分かりやすく、
連敗ボーナスと合わせて 負けている側に何度もチャンスが回ります。

`megaKey(p)` が発動中の技キーを返し、`canMega(p)` が発動可否をまとめて判定します。
**交代するとメガシンカは解けます**（`B.mega[p] = 0`）が、`megaUsed` は立ったままなので
控えが使い直すことはできません。

### 8.2.2 ダメージ計算

勝敗が決まったあと、両者のメガシンカ技を見て1回だけダメージを算出します。

```
dmg = (勝者が crit) ? 2 : 1
if (敗者が guard) dmg = 0        → 「まもりの かべ！」
相手の HP -= dmg
if (勝者が drain && dmg && 勝者が満タンでない) 勝者の HP += 1
```

あいこは通常ダメージなしですが、`storm` を持つ側が片方だけのときは
その側を勝者としてダメージ処理に合流します。両方なら相殺してダメージなしです。

### 8.2.3 UI

ゲージは各ゾーンの端（**その子から見て手前**）に細いバーで置きます。
**メガストーン型のボタンは、アリーナの自分のピックの隣に常設**します
（`.frow` / `index.html:146`）。

```
┌─── アリーナ ───────────────┐
│   [あおのピック] ❤❤❤   ●   │ ← あお側の石（その子から見て左）
│                            │
│   ◉  [あかのピック] ❤❤❤   │ ← あか側の石。満タンで虹に輝く
└────────────────────────────┘
[✊] [✌️] [✋]
[▓▓▓▓▓▓ きずな 53% ]
```

**設計判断: ゾーンではなくアリーナに置く**
当初はゲージの横に置いていましたが、**iPhone SE ではゾーンの余白が1pxしかなく、
石が画面下端から7pxはみ出していました**。ホームインジケータのスワイプ領域とも重なり、
40pxという大きさも手のボタン（90px）の半分以下で押しにくい状態でした。
ゾーンは画面の23%しかないため、**縦に伸ばす余地がありません**。

アリーナには余白があるので、ピックの隣なら **66px** まで大きくできます。
「自分のピックにメガストーンを使う」という意味も見た目で伝わります。

**設計判断: `.fighter` の外に置く**
`.fighter` の中に入れると攻撃アニメーション（`translateY` や `rotate`）に乗って
**石まで一緒に飛んでいきます**。`.frow` というラッパーで石と `.fighter` を横に並べ、
石はアニメーションの外に置いています。

**設計判断: ボタンを常に出す**
必要なときだけ出す作りだと、**そもそもメガシンカという行動があることに気づけません**。
いつも同じ場所にあって、使えるときだけ光る、という見せ方にしました。
石の見た目そのものが「まだ」「いまだ」を伝えるので、文字が読めなくても分かります。
使うとゲージが0に戻り、石も自動的にくすんだ色へ戻ります。

メガシンカできないピックのときは `.cantmega` で薄く落とし、押しても何も起きません。

ボタンは手と同じ **500msの長押し**で確定します。タップだと誤爆したときに、
せっかく溜めたゲージを無駄にしてしまいます。
進み具合は、手のボタンと同じく **円周を回るリング**で見せます（SVGの `stroke-dashoffset`）。

**注意: ゲージの描画は `B.busy` を下ろしたあと**
`canMega()` は `B.busy` を見るため、`newRound()` より先に `renderBond()` を呼ぶと
満タンでも石が光りません。`newRound()` の中で `renderZone()` と一緒に呼んでいます
（`index.html:1039`）。

### 8.2.3.1 発動の2段構え

メガシンカは **カットイン → 変身エフェクト** の順に見せます。

| 段 | 見せるもの | 長さ |
| --- | --- | --- |
| `megaIntro()`（`index.html:1292`） | メガストーンが虹に回りながら現れ、衝撃波が広がる。「◯◯と きずなが ひかった！」 | 約1.15秒 |
| `megaCutIn()` | 虹の放射光・広がる虹の輪・飛び散る虹の粒・ピックが光に包まれる。「◯◯ メガシンカ！」 | 約1.45秒 |

1つにまとめると「何が起きたか」が一瞬で流れてしまいます。
**まず石が光り、それから姿が変わる**という因果の順に分けることで、
メガストーンを使ったから変身した、という筋が伝わります。

### 8.2.4 レインボーで統一する（`index.html:16`）

メガストーンとメガシンカのイメージは虹なので、**メガシンカに関わる演出はすべてレインボー**にしています。
色は `:root` の2トークンに集約してあり、増やすときもここだけ見れば揃います。

```css
--rb :linear-gradient(90deg,#ff3b30,#ff9500,#ffd23f,#3ddc97,#23b8e8,#5b6bff,#c56bff,#ff3b30);
--rbc:conic-gradient(from 0deg,#ff3b30,…,#ff3b30);   /* 回転させる用 */
```

| 対象 | 見せ方 |
| --- | --- |
| 発動カットイン | メガストーンが虹に回る（`megaIntro()`）→ 虹の放射光・輪・粒（`megaCutIn()` / `index.html:1318`） |
| ピック隣のメガストーン | 満タンで `conic-gradient` が回り 虹に輝く |
| メガシンカ中のオーラ | 影の色を7色順に巡回 ＋ 背後で回る虹の輪 |
| きずなゲージ（満タン・発動中） | 流れる虹 |
| メガシンカボタン | 流れる虹 |
| メガ技のカットイン | 帯が虹、技名が虹グラデ文字 |
| メガ技のパーティクル | `FX.rainbow`（7色の星） |
| ずかんのメガ技バッジ | 流れる虹 |
| 発動音 | 虹の7色に合わせて 7音を駆け上がる |

**設計判断: オーラに `hue-rotate` を使わない**
虹色に巡回させる手軽な方法は `filter: hue-rotate()` ですが、
これは**ピックの写真そのものの色まで回してしまいます**。
実物の写真が別のポケモンの色に見えるのは避けたいので、
`drop-shadow` の色だけをキーフレームで順に差し替えています。

**設計判断: 暗幕は中央を薄く、端を濃く**
発動カットインは全面が虹なので、そのままだと文字が埋もれます。
暗幕を「中央ほど薄い」放射グラデにして、虹はピックの周りで見せつつ、
文字が乗る上下だけを落としています（勝敗画面とは逆向き）。
閃光も 520ms と短くし、虹が白飛びする時間を作らないようにしました。

**メガシンカできないピックのときは、ゲージに「この ピックは メガシンカ できない」と出します。**
ゲージだけ満タンになってボタンが出ないと、なぜ使えないのか分からなくなるためです。

発動中はゲージが紫に変わり「メガシンカ ちゅう！ あと ◯かい」を表示、
ピックには `.fighter.mega` のオーラ（`drop-shadow` の脈動）が付きます。

| 暗幕（`.dim` / `index.html:217`） | 放射光の上に中央ほど濃い `radial-gradient`。文字のコントラストを確保する |
| 紙吹雪（`.confetti` / `index.html:219`） | 26個の `<i>` に位置・色・速さ・**負の `animation-delay`** を散らす。負の遅延で最初から降っている状態にする |

**`pop()` ヘルパ**（`index.html:1409`）が `<%D%>` を実際の遅延に差し替えながら
カウンタを進めるので、要素の増減（チーム戦か、完全勝利か）に応じて
遅延が自動的に詰まります。手で数え直す必要がありません。

`.flip` を持つ要素は `transform: rotate(180deg)` と `pop` の `scale` が競合するため、
回転を含んだ専用のキーフレーム `popflip` に切り替えます。

`prefers-reduced-motion: reduce` では紙吹雪を消し、放射光と段階表示を止めます。
レイアウトはそのままなので、情報は何も失われません。

### 8.3.1 勝ち抜き（`index.html:1369`–`1392`）

| 関数 | 役割 |
| --- | --- |
| `knockOut(l)` | 敗者を回転させながらふっとばす。バナーは「あかの 2ばんめ ダウン！」 |
| `swapIn(p)` | 控えを**自分がわの画面外から**登場させる。ハートは3つで仕切りなおし |
| `resetFighter(p)` | 退場アニメーション（`fill:'forwards'`）を打ち消して素の状態へ戻す |

`swapIn()` の登場方向は `p === 1 ? 130% : -130%`。
それぞれ自分に近い側から出てくるので、どちらの子から見ても「自分の次のピックが出てきた」と分かります。

**`resetFighter()` が要る理由**: 退場アニメーションは `fill:'forwards'` で
`opacity:0` と大きな `transform` を残したままになります。
`getAnimations().forEach(a => a.cancel())` に加えて `style.opacity` / `style.transform` も
明示的に戻さないと、次のピックが透明なまま登場します。
`startBattle()`（「もういっかい」）と `swapIn()` の両方から呼ばれます。

### 8.3.2 残りメンバー表示（`renderRoster()` / `index.html:1067`）

ハートの下に、チームの人数ぶんの小さなピック型のマークを並べます。

| 状態 | 見た目 |
| --- | --- |
| 生存 | 不透明 |
| たおれた | 25%の透明度 |
| 出場中 | 黄色いリング（`box-shadow`） |

1対1のときは情報量がないので `hidden` にして出しません。
`.f2 .spin` の180°回転にそのまま乗るため、プレイヤー2側では
**出場順が右から左**になり、その子から見て正しい並びになります。

### 8.4 手の確定（長押し）

```
pointerdown → .holding クラス付与 → SVGリングが 0.5s かけて一周
                 ↓ 500ms 経過
              lock() で確定 → 「OK！ まってね」に置換
                 ↑
  pointerup / pointerleave / pointercancel でキャンセル
```

CSS のリングアニメーション（`index.html:140`、`transition .5s linear`）と
JS の `setTimeout(500)` を同じ長さにしてあり、**リングが一周した瞬間に決まる**という
視覚的なフィードバックが成立します。
`touch-action:none`（`index.html:137`）と `contextmenu` の抑止により、
長押し中のスクロールやテキスト選択メニューが割り込みません。

ボタンは毎ラウンド `renderZone()` で作り直されます。
イベントリスナも作り直されるため、前ラウンドのタイマーが残る心配がありません。

### 8.5 勝敗判定

```js
const BEATS = {gu:'choki', choki:'pa', pa:'gu'};  // index.html:469
const win = BEATS[a] === b ? 1 : 2;               // a はプレイヤー1の手
const lose = 3 - win;                              // 1↔2 の反転
```

**タイプ相性は未実装**で、勝者は常にハート1つ分のダメージを与えます。
あいこはダメージなしでやり直しとなり、回数制限はありません。

勝つために必要な勝利ラウンド数は **3 × 人数**（相手全員のハートを削り切る必要があるため）。
3対3なら最短9ラウンドで、あいこを含めると体感3〜5分ほどになります。

先鋒（`B.idx[w] === 0`）のまま勝ち切った場合は「ひとりで ぜんいん たおした！」を勝利画面に出し、
音声合成も「かんぜんしょうり！」に切り替えます（`finish()` / `index.html:1397`）。

## 9. 演出

### 9.1 攻撃シーケンス（`attack()` / `index.html:1232`）

```
技名バナー表示（攻撃側から読める向き）＋ 音声合成で技名を読み上げる
  ↓
カットイン                       約1300ms（reduced-motion 時 約600ms）
  ↓
ためる（縮んで小刻みに震える）      520ms  ＋ 低音のチャージ音
  ↓
突進（回転しながら相手へ）          360ms  ＋ 40ms間隔で軌跡パーティクル
  ↓
ヒット（大量パーティクル）          ＋ 画面シェイク260ms
  ↓ 敗者を白フラッシュさせながら押し込む（520ms）
  ↓ 260ms
帰還                              380ms
```

突進距離 `dy` は、攻撃側と防御側の中心座標の差の **72%**（`index.html:1238`）。
完全に重ねず手前で止めることで、相手のピックが隠れないようにしています。

### 9.2 カットイン（`cutIn()` / `index.html:1200`）

5層のレイヤーで構成されます（`index.html:319`–`334`）。

| 層 | 役割 |
| --- | --- |
| `.dim` | 背景を暗く落とす |
| `.flash` | 白フラッシュ（260msで消える） |
| `.band` | −12°傾いた帯。タイプ色のグラデ＋流れる集中線 |
| `img` | ピックが画面外から滑り込み、少し戻ってから反対側へ抜ける |
| `.ct` | 「◯◯の わざめい！」 |

集中線は `makeSpeedLines()`（`index.html:1185`）が 800×320 の Canvas に
長さ・太さ・濃度をランダムにした70本を描き、**左右2箇所に同じものを描く**ことで
`background-position` のループでシームレスに流れるようにしています。
生成結果は `speedLines` に**1度だけキャッシュ**され、以降のバトルで再利用されます。

### 9.3 パーティクル（`FX` / `burst()` / `index.html:921`）

`#fx` は `.arena` 全面を覆う単一の Canvas（`z-index:5`）。
`parts` 配列を単一の `requestAnimationFrame` ループ（`tick()`）で処理し、
パーティクルが尽きるとループを自動停止します（`fxRun` フラグ）。

エフェクト定義は10種で、それぞれ色配列・形状・個数・初速・重力・寿命・サイズ幅を持ちます。

| 形状 | 描画 |
| --- | --- |
| `circle` | 円（時間とともに縮む） |
| `drop` | 縦長の楕円 |
| `leaf` | 横長の楕円 |
| `shard` | 菱形 |
| `star` | 5芒星 |
| `bolt` | ランダムに折れる稲妻（線） |
| `ring` | 広がる輪。`delay` を個体ごとにずらして波紋にする |
| `arc` | 円弧（線） |

`ring` だけは初速0・`delay` ありという特殊な扱いで、
エスパー／フェアリーの「波紋が広がる」表現を、共通のパーティクル機構の上で実現しています。

### 9.4 サウンド（`sfx` / `index.html:877`）

音声ファイルを持たず、すべて Web Audio API で合成します。

| メソッド | 用途 |
| --- | --- |
| `tone(f, d, type, vol, slide)` | 単音。`slide` 指定で周波数をスイープ（チャージ音・ヒット音） |
| マスターバス | 全体を2.6倍に持ち上げ、`DynamicsCompressor` でピークを抑える |
| `noise(d, freq, vol)` | ホワイトノイズ＋バンドパス（突進音・カットインの衝撃音） |
| `say(text)` | SpeechSynthesis（ja-JP、rate 1.05、pitch 1.3） |

iOS の自動再生制限に対応するため、`unlock()` をユーザー操作の起点
（バトル開始・手のタップ・音ボタン・ピック選択）で呼び、AudioContext を生成・再開します。
`sfx.on` が false のとき、`tone`/`noise`/`say` はいずれも即座に return します。

音声合成は読み上げ内容が端末の音声エンジンに依存するため、
**ゲーム進行に必須の情報は必ず画面にも出す**方針にしてあります。

**設計判断: 効果音にマスターバスを通す**
読み上げ（`SpeechSynthesis`）は端末の音量そのままで鳴るのに対し、
Web Audio のゲインは小さいままだと**効果音が読み上げに埋もれます**。
そこで全ての音を一本のバスにまとめ、2.6倍に持ち上げたうえで
`DynamicsCompressor` を通してピークを抑えています。
個々の音量を上げるだけだと、音が重なったときに歪むためです。
読み上げ側も `utterance.volume = 0.85` と少しだけ下げて、ぶつかりを減らしています。

**設計判断: ヒット音を中高域に置く**
当初ヒット音は 90Hz→40Hz の低音でしたが、**iPhone の内蔵スピーカーは
この帯域をほとんど再生できず、当たった音が鳴らないように聞こえていました**。
いまは 2400Hz のアタック、520Hz の胴鳴り、800Hz の余韻を重ねて、
小さなスピーカーでも「当たった」と分かるようにしています
（`attack()` / `index.html:1232`）。

## 10. 対面プレイのための向き制御

本作の特徴的な設計で、要素ごとに回転の扱いを変えています。

| 要素 | 向きの扱い | 実装 |
| --- | --- | --- |
| プレイヤー2のゾーン全体 | 180°回転 | `.zone.p2` / `index.html:134` |
| プレイヤー2のピックとハート | 180°回転 | `.f2 .spin` / `index.html:188` |
| じゃんけんの掛け声バナー | **両向きに2つ表示** | `setBanner()` / `index.html:1110` |
| 技名バナー | **攻撃側の向きだけ** | `index.html:1240` |
| カットインの技名 | 攻撃側の向きだけ | `.ct.bot` / `.ct.top` |
| 勝敗表示 | **両向きに出すが、文言が違う** | `.result .w` ＋ `.w.flip` |
| 完全勝利の表示 | 両向きに2つ表示（文言は同じ） | `.result .sweep` ＋ `.sweep.flip` |
| 残りメンバー | 180°回転に追従 | `.f2 .spin` にそのまま乗せる |

**両者に関係する情報は2つ出し、片方だけの情報は1つだけ出す**という原則です。

勝敗表示だけはこの原則の一歩先を行き、**同じ位置に別々の文言**を出します。
勝った側には「あかの かち！」、負けた側には「あおの まけ」を、
それぞれ自分から読める向きで見せます（`finish()` / `index.html:1405`）。

```
画面の上端（あお側の手前）  あおの まけ     ← muted色・やや小さい
                          （ひとりで ぜんいん たおした！）
                            [勝ったピック]
                          （ひとりで ぜんいん たおした！）
画面の下端（あか側の手前）  あかの かち！   ← 黄色・大きい
```

両方に「あかの かち！」と出すと、負けた側の子が自分が勝ったと読み違えます。
`line(q)` と `wcls(q)` が「そのプレイヤーから見た結果」を組み立てます。

ピックの回転に `.spin` という内側のラッパーを噛ませているのは、
**外側の `.fighter` を攻撃アニメーション専用に空けておく**ためです。
もし `.fighter` 自身に `rotate(180deg)` を当てると、
Web Animations API が設定する `transform` と競合して回転が失われます。
この2層構造により、アニメーション側は向きを気にせず `translateY` や `scale` を書けます。

## 11. アクセシビリティと配慮

- `prefers-reduced-motion: reduce` を全編で尊重（`reduce` / `index.html:987`）
  - カットインを 1300ms → 600ms に短縮、集中線の流れを停止
  - ためる・突進・帰還のアニメーションをスキップ（ゲーム進行は同一）
  - 敗北の吹き飛びを 1100ms → 10ms に、勝利ピックの上下動を停止
- 手のボタンに `aria-label`、戻るボタン・削除ボタンにもラベルを付与
- `:focus-visible` のアウトラインを明示（`index.html:26`）
- 破壊的操作（ピック削除・バトル中断）は必ず確認モーダルを挟む（`confirmBox()` / `index.html:582`）
- ユーザー入力は `esc()`（`index.html:592`）で必ずエスケープしてから `innerHTML` に渡す

## 12. 既知の制限

| 項目 | 内容 |
| --- | --- |
| タイプ相性 | 未実装。ダメージはメガシンカ技でのみ変わり、タイプは見た目にのみ影響する |
| メガシンカの姿 | 専用の姿は用意せず、オーラと光で表現する（写真の追加登録が要らないようにするため） |
| あいこ | 回数制限なし。延々と続く可能性がある |
| 保存範囲 | 端末内のみ。Safari のサイトデータ消去で全ピックが失われる（エクスポート機能なし） |
| 画面の向き | 縦持ち前提。横持ちでのレイアウトは考慮していない |
| 対戦人数 | 2人固定（1人が1チームを操作）。CPU対戦なし |
| チーム人数 | 最大3対3。チーム内は重複なしのため、3対3には3枚以上の登録が必要 |
| 3対3の長さ | 最短9ラウンド。ハートを人数で変えていないぶん長丁場になりやすい |
| 音声合成 | 読み上げ品質・有無が端末依存 |
| 画像の最適化 | PNG固定。写真素材としては JPEG/WebP のほうが小さくなる |

## 13. 拡張のヒント

既存構造を活かしやすい拡張の入口を挙げます。

- **タイプ相性**: `TYPES` に相性テーブルを足し、`resolve()`（`index.html:1113`）の
  ダメージ計算を 1 固定から可変にする。「こうかは ばつぐんだ！」のバナーは
  `setBanner()` の第2引数（`sub`）がそのまま使える
- **HP数の変更**: `MAXHP`（`index.html:470`）を変えるだけで、ハート描画・初期化ともに追従する
- **新しいエフェクト**: `FX` に1エントリ追加し、`tick()` の `switch` に形状を1ケース足す。
  `TYPES` の第3要素から参照させる
- **ピックのエクスポート／インポート**: `store.all()` の結果は素の JSON 化が可能な構造なので、
  dataURL を含めたままファイル保存・読み込みができる
- **チーム人数を4以上に**: `SIZES` と `SIZE_LABEL`、`ORD` に要素を足す。
  ホームの縦スペースが足りなくなるため `.vs.n4` のコンパクト指定も必要
- **人数ごとにハートを変える**: `MAXHP` を関数化し、`startBattle()` の
  `B.hp[p] = B.team[p].map(() => MAXHP)` と `renderHearts()` の2箇所を通す
- **3人以上の対戦（プレイヤーを増やす）**: `B` の各値がプレイヤー番号キーの辞書、
  `lose = 3 - win` が2人前提。ここが唯一の固定箇所になる
